Ведомость эскизного проекта

На предыдущих стадиях разработки СУБД «Автовокзал» были составлены и утверждены следующие документы:
- Техническое задание на создание информационной системы СУБД «Автовокзал», разработанное на основании ГОСТ 34.602‑89 на написание ТЗ на автоматизированные системы управления от 01.01.1990 г.


Пояснительная записка к эскизному проекту

1. Общие положения

Данный документ является эскизным проектом на создание Системы Управления Базой Данных для предприятия «Автовокзал г. Алтай» (СУБД «Автовокзал»).
Перечень организаций, участвующих в разработке системы, сроки и стадии разработки, а также её цели и назначение указаны в техническом задании на создание информационной системы.

2. Основные технические решения

2.1 Решения по структуре системы

СУБД «Автовокзал» будет представлять собой клиент‑серверную систему управления реляционной базой данных, работающую в локальной сети автовокзала: центральная база размещается на сервере, а рабочие места кассиров и диспетчера обращаются к ней по сети как клиенты.
Система будет управлять реляционной базой данных, представляющей собой набор связанных между собой таблиц, доступ к которым осуществляется с помощью ключей и индексов. Сведения в одной таблице могут отражать сведения из другой, и при изменении данных в первой таблице эти изменения немедленно отображаются во второй. Таким образом будет достигнута непротиворечивость данных.

Общая структура базы данных:

- Пункты (населённые пункты отправления и назначения):
  - Код пункта.
  - Наименование пункта.
  - Регион (область).

- Маршруты:
  - Код маршрута.
  - Пункт отправления (код пункта).
  - Пункт назначения (код пункта).
  - Расстояние, км.
  - Тариф за километр, руб.

- Автобусы:
  - Код автобуса.
  - Государственный номер.
  - Модель.
  - Вместимость, мест.
  - Техническое состояние.

- Водители:
  - Код водителя.
  - Фамилия, имя, отчество.
  - Категория прав.
  - Стаж, лет.
  - Контактный телефон.

- Рейсы:
  - Код рейса.
  - Маршрут (код маршрута).
  - Автобус (код автобуса).
  - Водитель (код водителя).
  - Дата рейса.
  - Время отправления.
  - Время прибытия.
  - Свободные места.

- Пассажиры:
  - Код пассажира.
  - Фамилия, имя, отчество.
  - Документ, удостоверяющий личность.
  - Телефон.
  - Электронная почта.

- Билеты:
  - Код билета.
  - Рейс (код рейса).
  - Пассажир (код пассажира).
  - Номер места.
  - Стоимость, руб.
  - Статус.
  - Дата покупки.

2.2 Решения по режимам функционирования, работы системы

СУБД «Автовокзал» будет функционировать в многопользовательском режиме (несколько рабочих мест кассиров и диспетчера одновременно обращаются к единой серверной базе данных по локальной сети вокзала), а также будет способна:
- просматривать записи базы данных (в том числе при помощи фильтров и запросов — поиск рейсов по дате, маршруту, времени, подбор свободных мест);
- добавлять новые записи (рейсы, билеты, пассажиры, элементы справочников);
- изменять существующие записи (статус билета, число свободных мест рейса, данные справочников);
- удалять записи (неоплаченные и аннулированные билеты, закрытые рейсы);
- разграничивать доступ по ролям пользователей (кассир, диспетчер, контролёр, администратор);
- при входе в систему запрашивать имя пользователя и пароль;
- работать в автономном режиме на рабочем месте кассира при недоступности сервера с последующей синхронизацией накопленных операций.

2.3 Решения по численности, квалификации и функциям персонала АС

Указанные решения должны удовлетворять требованиям, приведённым в техническом задании на разработку системы.
Численность и квалификация персонала, обслуживающего АС, определяются составом ролей пользователей системы:
- Кассир — оператор售票ного окна; средняя профессиональная подготовка, обучение работе с интерфейсом продажи и возврата билета (до 2 часов); функции: поиск рейсов, оформление и продажа билета, приём оплаты, возврат билета.
- Диспетчер — специалист оперативного управления; знание предметной области перевозок; функции: формирование и корректировка расписания (рейсов), контроль отправления и прибытия, формирование отчётов по загрузке и выручке.
- Контролёр посадки — линейный персонал; функции: проверка и гашение билетов при посадке пассажиров в автобус.
- Администратор системы — ИТ‑персонал предприятия; квалификация: программист или администратор базы данных; функции: ведение справочников (пункты, маршруты, автобусы, водители), управление учётными записями и правами доступа, резервное копирование и восстановление базы данных.

Состав функций комплексов задач, реализуемых системой

Автоматизированная система должна выполнять следующие функции:
- вести справочник пунктов (населённых пунктов отправления и назначения);
- вести справочник маршрутов с расстоянием и тарифом;
- вести справочник автобусов (государственный номер, модель, вместимость, техническое состояние);
- вести справочник водителей (фамилия, имя, отчество, категория, стаж, контакты);
- зарегистрировать новый рейс в расписании (привязка маршрута, автобуса, водителя, времени отправления и прибытия);
- удалить или закрыть рейс из расписания;
- осуществить поиск рейсов по заданным параметрам с выводом числа свободных мест;
- оформить билет пассажиру на выбранный рейс с резервированием места;
- принять оплату билета и зафиксировать факт оплаты;
- произвести возврат билета с восстановлением свободного места;
- проверить и погасить билет при посадке пассажира;
- выдать справку о проданных билетах по рейсу;
- выдать справку о выручке за заданный период;
- выдать отчёт о загрузке автобусов (отношение проданных мест к вместимости).

2.4 Решения по составу программных средств, языкам деятельности, алгоритмам процедур и операций и методам их реализации

Для реализации АС будет использоваться среда программирования Microsoft Visual Studio и язык программирования C# (платформа .NET); в качестве системы управления базами данных — реляционная СУБД MS SQL Server; доступ к данным из приложения осуществляется через ADO.NET и ORM Entity Framework; интерфейс рабочих мест кассира и диспетчера — оконный (WPF).

Для продажи билета будет использоваться следующий алгоритм.
1. Кассир задаёт параметры поиска рейса (дата, пункт отправления, пункт назначения). Система формирует запрос к таблице «Рейсы» с соединением по внешним ключам с таблицами «Маршруты», «Автобусы» и «Водители» и возвращает список подходящих рейсов, для каждого вычисляя число свободных мест как разность между вместимостью автобуса рейса и количеством неаннулированных билетов на этот рейс.
2. Кассир выбирает рейс и пассажира; система проверяет условие «число свободных мест больше нуля». Если условие не выполнено, выдаётся сообщение «Мест нет», и процедура завершается без создания записи.
3. При наличии мест система в одной транзакции создаёт запись в таблице «Билеты» со статусом «оформлен» и номером места, уменьшает поле «Свободные места» соответствующей записи таблицы «Рейсы» на единицу и фиксирует дату покупки. Транзакция обеспечивает атомарность: при сбое на любом шаге изменения откатываются, и место не теряется.
4. Пассажир вносит оплату. При подтверждении оплаты из платёжного модуля система переводит статус билета в «оплачен»; при неподтверждении в течение контрольного времени билет автоматически переходит в статус «аннулирован», а счётчик свободных мест увеличивается на единицу, возвращая место в продажу.
5. На выходе формируется печатная или электронная квитанция (билет) с реквизитами рейса, номером места и суммой.

Для возврата билета будет использоваться следующий алгоритм.
1. Кассир вводит номер билета; система находит запись и проверяет её статус. Возврат разрешён только для билетов со статусом «оплачен» и не позднее момента отправления рейса; для статусов «использован», «аннулирован» и «возвращён» выдаётся отказ.
2. В одной транзакции система меняет статус билета на «возвращён», увеличивает поле «Свободные места» соответствующего рейса на единицу и формирует сумму к возврату согласно правилам тарификации.
3. Кассир выдаёт денежные средства, факт возврата фиксируется в записи билета.

Методом реализации указанных процедур является событийно‑ориентированное программирование форм интерфейса с вызовом параметризованных SQL‑запросов и хранимых процедур сервера базы данных. Контроль целостности (запрет продажи билетов сверх вместимости, обязательность существования связанного рейса и пассажира) обеспечивается ограничениями внешнего ключа и CHECK‑ограничениями на уровне схемы базы данных и дублируется проверками в бизнес‑логике приложения.

2.5 Модели структурного анализа предметной области

2.5.1 Диаграмма прецедентов (вариантов использования)
Диаграмма определяет взаимодействие внешних акторов с системой. Акторы: Пассажир, Кассир, Диспетчер, Контролёр, Администратор, а также внешняя Платёжная система. Основные варианты использования: «Поиск рейсов», «Регистрация пассажира», «Оформление билета» (включает обязательный шаг «Оплата билета»), «Возврат билета», «Проверка билета при посадке», «Управление расписанием», «Управление справочниками», «Формирование отчётов». Изображение приведено в Приложении А.

2.5.2 Диаграмма потоков данных
Контекстная диаграмма (уровень 0) содержит один процесс «ИС „Автовокзал“» и внешние сущности Пассажир, Кассир, Диспетчер и Администратор, Платёжная система, которые обмениваются с процессом потоками (запросы на поиск, данные пассажира, заявки на билет и возврат, платёжные сообщения, заявки на изменение справочников и расписания, выдаваемые билеты, квитанции, подтверждения оплаты, отчёты, сообщения об ошибках) при поддержке хранилища «База данных автовокзала».
Диаграмма 1‑го уровня декомпозирует процесс на восемь подпроцессов, каждый из которых связан с хранилищами данных D1–D7 (D1 Пункты, D2 Маршруты, D3 Автобусы, D4 Водители, D5 Рейсы, D6 Пассажиры, D7 Билеты):
- 1.0 Управление справочниками — вход: данные пунктов, маршрутов, автобусов, водителей от Администратора; выход: подтверждения и сообщения об ошибках; хранилища D1, D2, D3, D4.
- 2.0 Формирование расписания — вход: заявка диспетчера и ссылки на справочники; выход: записи рейсов; читает D1–D4, пишет D5.
- 3.0 Поиск и просмотр рейсов — вход: запрос пассажира или кассира; выход: список рейсов со свободными местами; читает D2, D3, D5, D7.
- 4.0 Оформление и продажа билета — вход: заявка на билет и данные пассажира; выход: бронь билета и сообщение о выделенном месте; читает D5, D6, пишет D7, обновляет D5.
- 5.0 Оплата билета — вход: платёж и счёт из процесса 4.0; выход: подтверждение оплаты и квитанция; обновляет D7, взаимодействует с внешней Платёжной системой.
- 6.0 Возврат билета — вход: запрос возврата и номер билета; выход: возврат места и сумма к возврату; читает и обновляет D7, обновляет D5.
- 7.0 Контроль посадки — вход: номер или скан билета; выход: статус «использован» либо отказ; обновляет D7.
- 8.0 Формирование отчётов — вход: период и параметры отчёта; выход: отчёты по продажам, выручке и загрузке; читает D5, D6, D7.
Изображения приведены в Приложениях Б и В.

2.5.3 Диаграмма «сущность — связь»
Диаграмма отражает логическую структуру базы, описанной в пункте 2.1. Сущности: Пункт, Маршрут, Автобус, Водитель, Рейс, Пассажир, Билет. Связи и их кардинальности: Пункт — Маршрут «один ко многим» в двух ролях (пункт отправления и пункт назначения); Маршрут — Рейс «один ко многим»; Автобус — Рейс «один ко многим»; Водитель — Рейс «один ко многим»; Рейс — Билет «один ко многим»; Пассажир — Билет «один ко многим». Связи «один ко многим» реализованы внешними ключами в таблицах. Изображение приведено в Приложении Г.

2.5.4 Диаграмма переходов состояний
Для сущности «Билет» определён жизненный цикл со следующими состояниями и переходами: исходное состояние «оформляется» по событию «создание заявки»; переход «оформляется → оплачен» по событию «успешная оплата»; переход «оформляется → аннулирован» по событию «неоплата или отмена»; переход «оплачен → использован» по событию «подтверждение посадки»; переход «оплачен → возвращён» по событию «возврат по заявлению». Состояния «использован», «возвращён» и «аннулирован» являются конечными. Изображение приведено в Приложении Д.

2.6 Словарь терминов

Автовокзал — предприятие, организующее отправку и прибытие междугородних и пригородных автобусов.
Маршрут — закреплённый путь следования между двумя пунктами с установленным расстоянием и тарифом.
Рейс — конкретное отправление автобуса по маршруту в назначенное время.
Билет — документ, удостоверяющий право пассажира на проезд на определённом месте рейса.
Вместимость — максимальное число пассажирских мест в автобусе.
Свободные места — разность между вместимостью автобуса рейса и числом оформленных неаннулированных билетов.
Кассир — оператор, осуществляющий продажу и возврат билетов.
Диспетчер — специалист, формирующий расписание и контролирующий выполнение рейсов.
Контролёр посадки — сотрудник, проверяющий билеты при посадке пассажиров.
